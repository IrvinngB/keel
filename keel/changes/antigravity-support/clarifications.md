# Clarifications: Experimental Antigravity support

Sources read: keel/config.yaml, keel/steering/*, proposal, exploration, specs/agent-registry, build/manifest.json (codex 155, gemini 221, kimi 301), bin/sdd, docs/install.md, CHANGELOG.md, test/.

## BLOCKER — must answer before design

### Q1: Which user-scope skills path does `install.user.map` target?
- Targets: Requirement "User-scope install" (specs/agent-registry/spec.md:86-92)
- Facts in code: `install.user.map` is a list, so writing two paths is technically possible (gemini already has two maps, manifest.json:282-293), but `installAgent` copies into every map entry and `userSkillDirs` (bin/sdd:118-123) derives doctor's user-level view from the same list. Gemini's user install writes `~/.gemini/skills` (manifest.json:287); its docs say `.agents/skills` aliases it. The exploration says `~/.gemini/config/skills` mirrors `~/.gemini/skills` locally, so a Gemini user install may already load into Antigravity, and vice versa. Issue #103 (secondary, unofficial): the CLI ignores `~/.agents/skills`, so reusing Codex's user map (`.agents/skills`, manifest.json:209-212) would be a silent no-op for the CLI.
- Risk if guessed wrong: silent no-op (wrong product), or double-loaded skills (both paths, or the Gemini mirror).
- Recommended default: ONE path, `~/.gemini/config/skills` (2.0 + IDE, the current primary product), with the CLI path `~/.gemini/antigravity-cli/skills` named in notes and docs as a manual alternative. Reasoning: two maps double the files for users of both products, and doctor's user-level warning (bin/sdd:443-446) only fires on directories listed in `userSkillDirs`, so it would not catch a Gemini mirror overlap. Cost: CLI-only users get nothing at user scope unless they read the docs; project scope (the main path) is unaffected. Also DO NOT put the user path in `skillsRead`: doctor and `skillsDirNotices` resolve `skillsRead` entries relative to cwd (bin/sdd:331, 431) and to `$HOME` (bin/sdd:122), so a path like `.gemini/config/skills` would produce project-level false checks. Keep `skillsRead: [".agents/skills"]`.
- Side effect to accept: because `skillsRead` contains `.agents/skills`, `userSkillDirs("antigravity")` includes `~/.agents/skills` (bin/sdd:122) and `skillsDirNotices` on a user install warns if `~/.agents/skills` holds sdd skills ("also reads .agents/skills ... twice", bin/sdd:330-334). Per #103 that may be a false warning for CLI users. Cost of fixing: code change in `bin/sdd` plus a test. Recommend: accept and note it, since the user-level layout of shared dirs is already flagged unverified (comment at bin/sdd:116-117).

### Q2: What `detect` and `projectMarkers` values avoid reporting Antigravity just because `~/.gemini` exists?
- Targets: Requirement "Detection does not overlap Gemini CLI" (spec.md:73-84)
- Facts in code: `detect` is used ONLY by `sdd doctor` (`found`, bin/sdd:429) and gates whether the unverified warning prints (bin/sdd:442). It does not influence `install`. `doctor` requires `r.detect` to be an array (`r.detect.length`); an empty array yields `tool n/a`, and then the unverified-fields warning appears only if `installedInProject` is true (bin/sdd:442). `projectMarkers` is read only for `method: plugin` (bin/sdd:214); for `copy` agents it is effectively decoration (codex uses `[]`, manifest.json:165). Detection of an installed project therefore comes from the AGENTS.md block by id (bin/sdd:219-220), not from markers.
- Risk if guessed wrong: false "tool found" on Gemini-only machines, or the unverified warning never shows (`n/a`) for a machine that has Antigravity but no install yet.
- Recommended default: `detect: ["~/.gemini/antigravity-cli"]` only (add `~/.gemini/antigravity` only if the docs confirm it as product-specific). Reason: `~/.gemini/config` also mirrors Gemini's skills locally and might exist for Gemini users, so it is a weaker marker; `antigravity-cli` is product-specific. `projectMarkers: []` (as Codex): they are unused for copy agents, and adding `.agents` would falsely match every Codex/Kimi/Gemini project. Cost: IDE-only users without `antigravity-cli` are shown `tool —` in doctor (no false positive, but the unverified warning is suppressed until they install). Add `detect` to `unverifiedFields`.

### Q3: Is `~/.gemini/AGENTS.md` the right `install.contextFile.user`?
- Targets: Requirement "User-scope install" (spec.md:86-92)
- Facts in code: Gemini's user context is `null` (manifest.json:297), so `installAgent` prints "append manually" instead of writing (bin/sdd:312). Codex sets `~/.codex/AGENTS.md`. A non-null value makes `sdd install antigravity --user` create/modify a file in the user's home (`upsertBlock` mkdir -p, bin/sdd:263). Docs list four candidates; the exploration marks `~/.gemini/AGENTS.md` and `~/.gemini/GEMINI.md` as global files, and `config/` variants are listed but not confirmed as precedence winners. Gemini CLI reads `~/.gemini/GEMINI.md`, not AGENTS.md, so writing `~/.gemini/AGENTS.md` does not touch Gemini's context (the earlier clash risk stays retired).
- Risk if guessed wrong: a Keel block written to a file Antigravity never reads (silent) or, with `GEMINI.md`, injected into Gemini CLI's global context.
- Recommended default: `~/.gemini/AGENTS.md` (first documented, not read by Gemini CLI by default, consistent with the project file name). List `userContextFile` in `unverifiedFields` (gemini already uses that exact name, manifest.json:226). Fallback if the orchestrator wants zero home-directory writes: set `null` like Gemini and print the manual-append hint. Cost of the default: writing a file nobody has verified is read; cost of `null`: user must append by hand, and the spec scenario "skills and the block appear only at the chosen paths" needs to change.

### Q7: "Double-discovery warning names Antigravity" and "lists both locations"
- Targets: Requirement "Shared-skills reader reporting", scenario "Double discovery" (spec.md:68-71)
- Finding: the doctor warnings use `r.displayName` (bin/sdd:445, 448), not the id, and list the directories. So the text will read "Antigravity ..." only if `displayName` is set to "Antigravity" (recommend `"Antigravity"`, matching the requirement wording). The reader list in the "shared with" notice uses ids (`antigravity`). Both fire only when `seen.length > 1 && (found || inProject)`, and `seen` is built from project-relative `skillsRead` dirs, so a project-level double copy needs a second entry in `skillsRead` (with `[".agents/skills"]` alone it can never fire for Antigravity project scope; only the user-level check at bin/sdd:443 can). Assumed: the scenario is satisfiable only at user level unless `skillsRead` gains a second dir; reword the scenario to "user level" or accept it as covered by the generic warning. No code change either way.

### Q8: Coexist-then-remove scenario needs an uninstall path
- Targets: Requirement "Project install into shared locations", scenario "Coexists with Codex or Kimi" (spec.md:34-37)
- Finding: FALSE as written. `bin/sdd` has no `uninstall`/`remove` for agents; only `guard install|remove` (bin/sdd:570). Nothing deletes a block. Assumed: reword to "installed, then re-installed (and the other block is untouched)"; if removal is tested, the test strips the block by hand. `upsertBlock` replaces only its own id's region (bin/sdd:255-261), so coexistence is safe. Two additional edge cases to test: install order antigravity-then-codex, and a malformed marker in AGENTS.md (`assertMarkersSane` refuses to write, bin/sdd:235-242, 300).

### Q9: `dialect()` and `sdd status/next` behaviour with a shared AGENTS.md
- Targets: none in spec (missing edge case)
- Finding: `dialect()` (bin/sdd:226-229) picks the FIRST agent in registry order whose block exists. Where the antigravity row sits in `AGENT_IDS` decides which invoke string `sdd next` prints for a repo with both Codex and Antigravity blocks. Antigravity invocation is `/<skill-name>` (exploration), differs from Codex `$sdd-...`. Assumed: place the row after `kimi` so existing repos keep their current `next` output; `invoke.cmd: "/sdd-{name}"`, `agent: "sdd-phase-{short}"`, `skill: "{name}"`. Spec is silent on `invoke`: add a line in the design.

### Q10: `sdd install antigravity --project` also runs the commit guard

The spec's "no other agent directory is created" and "only `.agents/skills/**` and the AGENTS.md block" would be violated in a git repo (`.git/hooks/pre-commit`, outside the tree listing but real).
